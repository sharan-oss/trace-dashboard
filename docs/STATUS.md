The drill-down is therefore scoped by **payment day** and **deliberately disagrees** with People — `tests/overview-day-drilldown.test.ts` asserts the disagreement, so a future "fix" that swaps in the cohort filter fails the suite. That is now the third place this distinction is encoded (the other two: `v_customers_attributed`'s header, and `src/lib/queries/customers.ts`'s). Each L2 row shows the buyer's acquisition day, flagged when it precedes the range — the explanation lands in place instead of in a doc. **Reconciliation is structural, not hoped for**: `overview_day_payments` takes the identical window arguments as `overview_revenue_daily` and carries the identical predicate text plus `= p_day`, so its rows are a strict narrowing of the graph's own input set (verified: 30/30 days match on both arms, and Σ over days = `overview_kpis`). An RPC rather than direct PostgREST because the L2 dedupe guard is an anti-join on a non-FK pair (`external_order_id` ↔ `payments.order_id`) that PostgREST cannot express — re-implementing it in TS would have recreated the very "two definitions of one rule" hazard behind the report. Two live-data traps the implementation respects: synced `external_payments` rows carry an **empty** `customer_name` (so the L2 arm falls back to `customers.name`), and some L1 payments have a **null `customer_id`** yet still count in the graph (so the L1 arm must not inner-join `customers`). Keyboard path is a native "Open a day…" select in the chart footer — Recharts' `accessibilityLayer` focuses the SVG and arrow-keys the active point, but **Enter on a focused `<svg>` dispatches no click** and there is no keydown passthrough, so the chart alone leaves keyboard users with no way in. Revenue tab only: the chart tab is local `useState`, so a shared `?day=` link would always land on Revenue regardless. 372 tests.
